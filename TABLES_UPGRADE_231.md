# Upgrade 231 — Automatic station ticket staging on kitchen acceptance

Added `gs_auto_route_order_on_acceptance` as an `AFTER UPDATE OF status` trigger on `gs_orders`. On the authoritative `new -> preparing` transition (via `gs_update_kitchen_status`), it calls the protected `gs_route_confirmed_order` RPC from upgrade 229. The RPC stages one ticket per preparation station, including only that station's product lines. Unmapped products, disabled destinations, or zero tickets cause the transaction to abort, leaving the order unaccepted rather than silently losing it. Duplicate tickets are prevented by the existing unique `(order_id, station_key)` constraint. The new permission-protected `gs_list_order_station_tickets(order_id)` RPC allows inspection of staged tickets.

**Important:** Existing `gs_staff_review_public_request` marks a public request accepted but creates its kitchen order with status `new`; routing therefore starts when kitchen staff advance that order to `preparing`, not at the public-request approval moment. No real printer delivery, device acknowledgement, or offline queue has been implemented. No Flutter compilation or live Supabase migration test was performed. Apply SQL migrations in order and test with staging data, including unassigned products, retry/idempotency, and the public order workflow.
